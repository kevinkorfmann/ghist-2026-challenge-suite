## Context established from the code

Both engines parameterize `(post_decline_fraction ν, scaled_time T)` in log space (`optimization.py:16-17`), convert θ → N_a with the diploid relation θ = 4N_aμL (`sfs_baseline.py:218`, `dadi_reference.py:24`) and T → generations with the 2N_a convention (`sfs_baseline.py:219`, `dadi_reference.py:25`), both re-verified against the retained endpoint at `optimization.py:145-146`. The retained-fit bookkeeping is genuinely strong: `validate_retained_outcomes` recomputes selection, origin-best, agreement counts, raw neighborhood probes and the physical parameters from `optimizer_attempts`, and its tie-break order (`optimization.py:100`) does match the append order in `run_optimizer` (coarse→fine per origin, then refinements), so selection is reproducible. I found no defect in that core accounting.

## Findings

**1. Engine-asymmetric L-BFGS-B budget makes `converged` mean different things for dadi and moments — HIGH**
`optimization.py:31-33`: `maxfun = 15000 if moments else 500` and `maxiter = 500 if moments else 15000` — the two values are mirror-transposed between engines. Meanwhile both engines declare `maxiter=500` to `validate_fit_settings` (`sfs_baseline.py:180`, `dadi_reference.py:47`), which contradicts the contract's applied 15000 for dadi. Mechanism: with `approx_grad=True` and 2 parameters, each iteration costs ≥3 objective calls, each of which is a 3-grid extrapolated diffusion solve (`dadi_reference.py:53-62`); a 500-evaluation cap binds long before `maxiter=15000` can, and scipy then returns `warnflag=1`, i.e. `converged=False` (`optimization.py:236`). That flag is a hard gate at `optimization.py:60-61`, is required by the consumer guard (`bottleneck_consumer_guard.py:90-93`) and by `record_replica`, where one non-converged replica aborts every interval (`bootstrap_bottleneck_sfs.py:171-177`). Whether this is a transposition typo or a deliberate undocumented budget, the consequence is the same: dadi fits can be declared non-converged for budget reasons while moments fits are not, so the shared `require_converged` gate is not engine-comparable. *Verification:* run one `fit_two_epoch_dadi_spectrum` and inspect `optimizer_arm_summary[*].reported_converged` plus per-attempt `optimizer.evaluations`/`message`; if evaluations pile up at ~500 with `warnflag=1`, the cap binds and the contract values should be swapped (or justified in writing).

**2. Bootstrap replicates get warm-started with 1/12th to 1/32nd the search effort of the reference — HIGH (uncertainty claim)**
`bootstrap_bottleneck_sfs.py:143` sets `initial` to the reference point estimate and `_fit_replica` (`:70-79`) fits each replica with `restarts=2`, so origin 0 starts *at* the reference MLE and only one cold start remains (`optimization.py:175-176`). The reference fit used 24 (moments, `sfs_baseline.py:130`) or 64 (dadi, `dadi_reference.py:34`) cold starts. Because selection takes the minimum objective, the warm start never hurts optimization — the defect is the *asymmetry*: if a replica's global optimum lies away from the reference, 2 starts are far less likely to find it than 24/64, so replicate optima are preferentially retained in the basin containing the reference. Replicate dispersion is then a lower bound and the percentile interval at `:204` is partly an optimizer-effort artifact rather than pure resampling variability. Operationally the same choice is brittle in the other direction: `record_replica` demands `require_agreement=True`, i.e. ≥2 of only 2 origins within 0.1 log-likelihood (`optimization.py:62-63`), so one stray cold start kills all intervals. *Verification:* re-fit ~20 replicate spectra twice — once as coded, once with `initial=None` and restarts matched to the reference — and compare the per-replica estimates and the resulting 95% interval widths; also count how often the warm origin supplies `best_restart` in `optimizer_origin_best`.

**3. The readiness summary scores optimizer quality from self-reported JSON fields it never validates — MEDIUM**
`summarize_bottleneck_readiness.py:74-76` counts `optimizer.converged`, `restarts_within_0_1_log_likelihood >= 2` and `passes_finite_neighborhood_check` straight out of each fit file. Nothing in this module calls `validate_optimizer_contract` or `validate_retained_outcomes`, so none of the inconsistencies the other two consumers catch (selected endpoint ≠ best retained endpoint, forged agreement counts, probe/flag mismatch, source drift) can be detected here. The only identity check, `:43`, is gated on `config['schema'] == 'bottleneck_target_length_v3'` and compares against contracts stored *in the same protocol file*; spectrum binding is likewise skipped for schema `v1` (`:34`). Second mechanism in the same claim: `complete` at `:87` requires only zero `incomplete` and zero `failed` counts, never `fitted == planned`, so a result file that exists but contains neither `fit` nor `failure` nor `incomplete` is counted as a complete, non-failed case while contributing nothing to the error quantiles at `:78-83`. *Verification:* over an existing summary directory, call `validate_optimizer_contract(result['fit'], engine=method)` for every case and count raises; separately assert `summary[g]['fitted'] == summary[g]['planned']` for every group whenever `complete is True`.

**4. The two source-identity mechanisms use disjoint key spaces, so neither proves the executed code was the hashed code — MEDIUM**
`optimizer_contract` hashes files relative to the *imported module* (`optimization.py:23-25`) and keys them `ghist_bottleneck/optimization.py`, `ghist_inference/validation.py` (`:38`). `source_manifest` hashes files relative to the *script's* repo root (`bottleneck_consumer_guard.py:11,20-33`) and keys them `src/ghist_bottleneck/optimization.py`. The key sets never intersect, and no code compares the overlapping files, so under a non-editable install or a mixed `PYTHONPATH` `require_bundle` can certify repo bytes while the fits were produced by different installed module bytes. `bootstrap_bottleneck_sfs.py:116-120` has the same `src/`-prefixed repo view. *Verification:* in one process print `ghist_bottleneck.optimization.__file__`, `optimizer_contract('moments')['source_sha256']` and `source_manifest(producer)`, and assert the `ghist_bottleneck/*.py` and `ghist_inference/validation.py` digests equal their `src/`-prefixed counterparts; a single such assertion inside `require_bundle` would close the gap.

**5. `callable_sequence_length` cannot be bound to the projection that defines it, and it divides N_a directly — MEDIUM-HIGH (untested assumption, not a crash)**
The projection is chosen *inside* `projected_sfs_from_vcf` from the called-depth distribution (`sfs_baseline.py:68-76`), after which every record with `called < projection` is silently dropped (`:85-86`), so `projected_records` can be below `segregating_records`. `spectrum_exposure` (`:106-119`) correctly refuses to invent exposure from a variant-only VCF, but when the caller does supply `callable_sequence_length` it is only range-checked (`0 < L_c ≤ L`); nothing verifies it is the callable length *at ≥projection called haplotypes*, and neither wrapper (`sfs_baseline.py:139`, `dadi_reference.py:136`) exposes `projection=`, so the caller cannot know the depth threshold their exposure must match. Since N_a = θ/(4μL_c) (`sfs_baseline.py:218`, enforced at `optimization.py:145`) and generations = 2·N_a·T, an exposure/projection mismatch propagates as a proportional bias into both reported demographic quantities. This bites exactly in the masked-data case where `callable_sequence_length` is mandatory; with no missingness the guard at `:110-115` makes it moot. *Verification:* on a VCF with missingness, log the called-depth histogram and `projected_records/segregating_records`, then refit with the projection pinned and `L_c` recomputed as the span with ≥projection called haplotypes; N_a should move by the ratio of the two exposures.

## Unresolved scientific gates

- **No test exercises a real likelihood surface.** Both test files monkeypatch `fmin_l_bfgs_b` or the fitters (`test_bottleneck_optimization.py:28,48,66`, `test_bottleneck_consumer_contract.py:176-201`); the finite-neighborhood machinery is validated only against toy quadratics (`:17`). Convergence, identifiability of (ν, T), and numerical accuracy of either engine's two-epoch solution are untested in scope — the suites test bookkeeping, not inference.
- **Corner-masking convention is library behaviour I did not execute.** The hypergeometric projection (`sfs_baseline.py:90`) deposits mass in bins 0 and `projection`; whether `ll_multinom` and `optimal_sfs_scaling` exclude them (and therefore whether θ is the unconditional 4N_aμL) depends on `moments.Spectrum`/`dadi.Spectrum` default corner masks. Gate: assert `data.mask[0] and data.mask[-1]` for both engines and confirm `optimal_sfs_scaling` is Σdata/Σmodel over unmasked bins.
- **Block-bootstrap independence is not established.** `complete_block_spectra_from_vcf` requires one contiguous chromosome (`sfs_baseline.py:281`) and resamples 2 Mb blocks; inter-block LD is unmodelled and coverage is explicitly disclaimed (`bootstrap_bottleneck_sfs.py:191`). Independent chromosome/pedigree units would be the defensible resampling unit; nothing here upgrades the interval beyond "unvalidated percentile". Related labelling hazard: `latent_covariance` (`:205`) covers only 2 of the 3 quantities listed in `columns` (`:201`).
- **Model adequacy and polarization are assumed, not tested.** A single instantaneous size change, constant μ = 3.42e-8, no structure/growth/selection, and error-free `AA` annotations (`sfs_baseline.py:47-56`) are biological assumptions; mispolarization that is self-consistent in `AA` is undetectable by these files. The `generations = 2N_aT` convention is also never asserted against either library's docstring in scope.
- **Lesser note, not counted as a finding:** `log_starts` consumes one fewer RNG draw when `initial` is given (`optimization.py:175-176`, pinned by `test_bottleneck_optimization.py:74-79`), so warm-started and cold-started runs with the same seed do not share random starts — the docstring's "preserve historical RNG consumption" holds only within each variant.
